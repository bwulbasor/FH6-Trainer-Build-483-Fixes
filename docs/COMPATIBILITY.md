# Investigating compatibility with another game build

This guide is for a maintainer or AI agent working with the owner's permission. Start with read-only inspection. Do not disable security protections or bypass DRM or anti-cheat; do not modify the executable or saves as a shortcut. Work offline and avoid guessing addresses. A trainer attach or a hook installation alone does not prove that the requested visual effect works.

1. Record the executable's file version, platform, build, trainer revision, and relevant logs. Confirm the game is fully loaded into free roam and that the selected process has a game window. Preserve the existing working version and source before experimenting.
2. Read `Services/GameProcessService.cs`, `Services/CheatService.cs`, `Cheats/Weather/WeatherChanger.cs`, `Cheats/Season/DirectSeasonChanger.cs`, `Cheats/Season/GameThreadInvoker.cs`, and the Unlocks view and view model. Trace the path actually used on the target build: the fallback getter hook and the direct weather manager path are different mechanisms.
3. Compare signatures and instruction semantics against the actual executable. Require unique matches and validate pointer ownership, readable ranges, expected data types, and process lifetime. A matching version string or a familiar offset is insufficient. On 6.483.970.0 the direct path is explicitly version-gated and validates signatures; preserve that fail-closed behavior. Treat existing offsets as documentation of that build, not a recipe for a new one.
4. For season changes, identify the supported game's actual season state and visual transition path, calling conventions, object lifetime, and owning thread. The experimental path invokes the game function on a verified update thread; unsafe calls from an arbitrary remote thread crashed during development. Do not reuse a call target or thread assumption without independently verifying it on the new build.
5. For weather and time, verify the manager and script state, how current and requested values interact, and how changes are restored. Test one control at a time. The script is shared by weather and time: check both activation orders and restore behavior. Avoid overlapping independent trainers or tests that could overwrite each other's saved state.
6. Test in offline free roam using a temporary, bounded change with cleanup and clear status reporting. Check process responsiveness, in-game values, persistence, restoration, and visible results. Ask the player to confirm effects where needed. A value reaching its maximum does not establish that heavy snow, a gale, or fog is visible.
7. Add build-specific checks and only expose controls whose behavior is understood. Document the exact build, observed results, unverified controls, and limitations. Build the trainer and have the player verify the packaged app, not just an internal harness. Preserve attribution and the GPL license.

For this build, fog remained unresolved. The game's time-of-day asset contains named fog-related skies, but finding a name or changing the general atmosphere intensity did not prove visible fog. Do not label an unverified candidate as working.
